# Data Model

## Status

This documents the first implemented PostgreSQL schema and the broader
conceptual model for the MVP. Retention and deletion behavior still need
decisions. All private health records must be associated with an owner and
protected by backend authorization.

## First check-in slice

The first vertical slice is one user-authored check-in that can be created and
listed in history through the backend. Its fields are:

| Field | Meaning | Rule |
|---|---|---|
| `recorded_date` | Calendar date the check-in describes | Required; date only |
| `pain_level` | User-reported pain | Required integer from 0 to 10 |
| `daily_impact` | User-reported effect on daily activities | Required: `NOT_AT_ALL`, `A_LITTLE`, or `A_LOT` |
| `symptoms` | Selected symptoms | Zero or more: pelvic pain, bloating, fatigue, back pain, nausea; the Figma “More” options need defining |
| `notes` | Optional free-text note | Optional; up to 2,000 characters |

Cycle information is deferred from this first slice. These are personal
observations, not clinician-verified facts or diagnostic conclusions.

### API ownership contract

The mobile app must not submit an owner ID as authority. It sends a Firebase ID
token; the backend verifies the token and sets the entry owner from its verified
Firebase UID claim. List queries must be scoped to that verified UID.

Illustrative request to `POST /api/v1/check-ins`:

```json
{
  "recordedDate": "2026-11-15",
  "painLevel": 4,
  "dailyImpact": "A_LITTLE",
  "symptoms": ["PELVIC_PAIN", "FATIGUE"],
  "notes": null
}
```

The request deliberately has no `userId`. A corresponding
`GET /api/v1/check-ins` returns only the authenticated user's entries. The API
response includes each entry's generated ID and fields; its owner must not be
selectable by the client.

## Candidate records

### User

Firebase Authentication is the identity provider. The backend can use the
verified Firebase UID as the owner key for this first slice; a separate user
profile record is not needed until a feature requires app-owned profile data.

| Field | Meaning |
|---|---|
| `firebase_uid` | Stable owner identifier from a verified Firebase token |
| `created_at` | Optional first-seen timestamp if the backend later needs a local user record |

Only add profile details that a required feature needs.

### Symptom entry

A user's record of symptoms and impact for a date or period.

| Field | Meaning |
|---|---|
| `id` | Stable entry identifier, generated by the backend |
| `firebase_uid` | Owner from the verified Firebase token |
| `recorded_date` | Calendar date the entry describes |
| `pain_level` | Required user-reported integer from 0 through 10 |
| `daily_impact` | Required value: `NOT_AT_ALL`, `A_LITTLE`, or `A_LOT` |
| `notes` | Optional free-text note |
| `created_at` | When the entry was created |
| `updated_at` | When the entry was last changed |

An entry may have one or more symptom details:

| Field | Meaning |
|---|---|
| `id` | Stable symptom-detail identifier |
| `entry_id` | Parent entry |
| `code` | Selected symptom code, such as `PELVIC_PAIN` or `FATIGUE` |

The PostgreSQL schema stores these codes in `check_in_symptoms`, keyed by
`check_in_id` and `symptom_code`. The known choices are pelvic pain, bloating,
fatigue, back pain, and nausea. The Figma “More” control indicates additional
choices, but those choices need to be agreed before they are added. Symptoms
have no separate severity in this first data model; pain is captured by
`pain_level`.

### Cycle information

Deferred from the first check-in slice. If added later, define its fields and
relationship to entries before implementing it; do not make cycle information
required.

### Appointment preparation item

A user-authored question or concern for an upcoming medical appointment.

| Field | Meaning |
|---|---|
| `id` | Stable item identifier |
| `user_id` | Owner reference |
| `kind` | Question or concern |
| `text` | User-authored content |
| `created_at` | When the item was created |
| `completed_at` | Optional marker that the item was discussed |

### Educational resource

Content made available to users by the app.

| Field | Meaning |
|---|---|
| `id` | Stable resource identifier |
| `title` | Display title |
| `content` | Educational text or a reference to it |
| `source` | Attribution or source reference |
| `reviewed_at` | Date the content was last reviewed |

Content authorship, sourcing, and review workflow must be decided before
publishing resources.

## Derived information

Health-history views, dashboard activity, and appointment symptom summaries
should be derived from the user's entries and selected date range. Do not
persist an inferred diagnosis or a pattern as a medical conclusion.

## Relationships

- One Firebase UID owns many symptom entries.
- One symptom entry may have many symptom details.
- Optional cycle information is associated with the user's chosen entry or
  date range; the exact relationship is undecided.
- One user owns many appointment preparation items.
- Educational resources are app content, not private user health records.

## Data rules

- A symptom entry is a user's observation, not a clinician-verified fact.
- All private records use the owner UID from a verified Firebase ID token and
  must be scoped to that UID on every backend operation.
- Validate `pain_level` to the inclusive range 0–10 and restrict
  `daily_impact` to the agreed three values at the backend boundary.
- Reject unsupported symptom codes and notes longer than 2,000 characters.
- Notes and symptom information are sensitive; do not include them in logs.
- Collect only data needed for MVP features; cycle information and notes stay
  optional.
- Define deletion behavior, retention, and backup handling before real user
  data is stored.
- Use fictional values in development and tests.
